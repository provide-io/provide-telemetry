TWO DISTINCT FAILURE SIGNATURES
-------------------------------
Signature 1 — the export failed:

  expected /v1/logs export, saw []
  emitted_logs: 1, export_failures_logs: 1, export_latency_ms_logs: 0.0

  The record was emitted and the export attempt FAILED, so nothing reached the
  collector. Consistent with the collector socket being gone or refusing.

Signature 2 — the export SUCCEEDED but landed elsewhere:

  expected /v1/traces export, saw []
  emitted_traces: 1, export_failures_traces: 0, export_latency_ms_traces: 1.08

  Zero failures and a real latency reading mean the exporter completed a
  request. The fake collector this test was asserting against saw nothing, so
  the request went somewhere else.

LEADING HYPOTHESIS (not yet proven)
-----------------------------------
Signature 2 is the informative one: a successful export that the asserting
collector never saw points at process-global OTLP endpoint configuration being
crossed between tests running concurrently in the same binary. Test A installs
its collector endpoint, test B overwrites it, and A's span is delivered to B's
collector — which is why the failure moves between tests run to run and why
serial execution is clean.

This is the same class of defect that required acquire_test_state_lock() in
rust/tests/parity_event_name_test.rs during Plan 1: process-global telemetry
state read and written by tests cargo schedules in parallel.
